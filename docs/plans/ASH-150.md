# ASH-150 — Fail closed on staff remove sessions, enforce `isActive` in AuthGuard

- Linear: [ASH-150](https://linear.app/ashinaga/issue/ASH-150/auth-fail-closed-on-staff-remove-sessions-and-enforce-isactive-in)
- Follow-up from [ASH-142](https://linear.app/ashinaga/issue/ASH-142) / [PR #180](https://github.com/Ashinaga-UK/ashinaga/pull/180)
- Base: `origin/test` @ `771a2cf5` (merge of #165). Better Auth `1.6.33`.
- Status: **plan only**. This PR does not change any application code.

## 1. Goal

A staff member who has been removed (`staff.is_active = false`) must lose API access straight away,
including through sessions created **before** the removal. Two changes:

1. `UsersService.removeStaff` must not report success while the target's sessions still exist.
2. `AuthGuard` must reject a staff session whose staff row is inactive. Scholars stay as they are.

## 2. What the code does today (verified on `origin/test`)

| Area | File / symbol | What it does |
|---|---|---|
| Remove staff | `apps/api/src/users/users.service.ts` → `removeStaff` (L131–199) | In a transaction: locks the active super-admins, then the caller, then the target (`FOR UPDATE`), and sets `isActive = false`. **After** the commit, it runs `database.delete(sessions)` in a `try/catch` that only calls `console.error`, so the response is still `{ success: true }` if the delete fails. |
| Already inactive | same, L174–176 | Returns `{ success: true, alreadyInactive: true }` and **skips** the session delete. A retry after a failed delete therefore never cleans up. |
| AuthGuard | `apps/api/src/auth/auth.guard.ts` → `AuthGuard.canActivate` | Calls `auth.api.getSession`, then sets `request.user = { id, email, userType }`. It never reads `staff`. Every error is turned into `401 Authentication failed`. |
| StaffGuard | `apps/api/src/auth/staff.guard.ts` → `StaffGuard.canActivate` | Requires `userType === 'staff'` **and** a staff row with `isActive`. A missing row gives 403. Sets `staffRole`. |
| Sign-in hook | `apps/api/src/auth/session-guard.ts` → `assertSessionAllowed`, wired in `auth.config.ts` `databaseHooks.session.create.before` | Rejects inactive staff with `APIError('FORBIDDEN', { code: 'ACCOUNT_DEACTIVATED' })`. A missing staff row is allowed (during invitation signup the session is created before the staff row). It does **not** look at `userType`. |
| Session storage | `auth.config.ts` | No `session.cookieCache` and no `secondaryStorage`, so `getSession` reads the `session` table on every request. Deleting the rows therefore revokes the cookie at once. |
| Index | `apps/api/src/db/schema/users.ts` → `staff.userId` | `.unique()`, so a lookup by `user_id` is a single index probe. |
| AuthGuard users | `users`, `requests`, `documents`, `files`, `avatars`, `annual-updates`, `goals`, `tasks`, `proposals`, `resources`, `faqs`, `announcements`, `scholars`, `scholar-notifications` controllers | Around 40 handlers. Every one of them gets the new check without being edited. |
| Tests | `users.service.spec.ts` (`removeStaff` block), `session-guard.spec.ts`, `staff.guard.spec.ts`, `test/integration/staff-deactivated-signin.integration.spec.ts` | There is **no `auth.guard.spec.ts`**. No integration test calls `DELETE /api/users/staff/:userId` through the real guards. |

## 3. Corrections to the ticket

1. **Delete sessions inside the transaction instead of "retry, then 500".** The ticket suggests
   deleting after the deactivate and returning 500 if that fails. That leaves a committed
   `isActive=false` together with live sessions, and the client receives an error for a change that
   actually happened. Running the delete inside the same transaction as the `UPDATE` makes the
   result all-or-nothing. Either both happen and the API returns 200, or the whole thing rolls back
   and the API returns 500 with the staff member still active, so the admin can simply retry. No
   retry loop is needed.
2. **The `alreadyInactive` path must also delete sessions.** Today it returns before the delete.
   Rows can survive from older failures (the current swallowed `catch`) or from the sign-in race
   described in section 6. Calling remove again should clean them up. This changes the existing unit
   test `does nothing for a staff member who is already inactive`.
3. **One definition of "deactivated staff".** `assertSessionAllowed` already owns the rule
   "a staff row exists and `isActive === false`, while a missing row is allowed". AuthGuard should
   reuse that predicate rather than add a third copy of the query (StaffGuard has the second).
4. **Response code.** AuthGuard's catch-all turns every error into 401. For a deactivated staff
   session we return **403 with `code: 'ACCOUNT_DEACTIVATED'`**, reusing the constants in
   `session-guard.ts`. This matches the sign-in hook and StaffGuard, and gives the deferred frontend
   auto-sign-out a stable signal to act on. The catch block has to rethrow
   `ForbiddenException`/`UnauthorizedException`, as StaffGuard already does. Any other error
   (for example a failed DB lookup) still becomes 401, so the guard fails closed.

## 4. Scope challenge

- **What already solves part of this:** `assertSessionAllowed` (the predicate), StaffGuard (defense
  in depth, unchanged), and the transaction plus lock order in `removeStaff` (the delete joins it).
  Better Auth's `internalAdapter.deleteSessions(userId)` exists, but it cannot join our Drizzle
  transaction (see shape B).
- **Minimum change:** 3 source files plus 3 test files (1 new). No new classes, services, modules,
  routes or migrations. This is under the 8-file / 2-class threshold.
- **Deferred:** frontend auto-sign-out, moving AuthGuard-only staff routes to StaffGuard, scholar
  deactivation, and Microsoft OAuth UX. See section 11.
- **Flow coverage:** no new `/api/` routes, pages or nav items, so `pnpm check:flow-coverage` stays
  silent. Coverage is still required by this plan (section 8).

## 5. Two shapes

The change touches a shared boundary (every AuthGuard route), so both shapes were sketched.

**Shape A (chosen): deactivated-staff predicate in `session-guard.ts`, used by the hook and by
AuthGuard; session delete inside the `removeStaff` transaction.**

```ts
// session-guard.ts
export async function isDeactivatedStaff(userId: string): Promise<boolean>; // row exists && !isActive
export async function assertSessionAllowed(session: { userId: string }): Promise<void>; // uses it

// auth.guard.ts
if (userType === 'staff' && (await isDeactivatedStaff(session.user.id))) {
  throw new ForbiddenException({ code: ACCOUNT_DEACTIVATED_CODE, message: ACCOUNT_DEACTIVATED_MESSAGE });
}

// users.service.ts removeStaff, inside database.transaction(tx => …)
await tx.delete(sessions).where(eq(sessions.userId, targetUserId)); // both active and alreadyInactive branches
```

**Shape B (rejected): revocation owned by Better Auth.** Commit the deactivate, then call
`(await auth.$context).internalAdapter.deleteSessions(targetUserId)` with one retry and throw 500
on failure. AuthGuard would add its own `staff` query.

```ts
async function revokeAllSessions(userId: string): Promise<void>; // not implemented
```

**Why A:** A hides the whole policy ("removal is atomic with revocation" and "a deactivated staff
member has no access") behind one predicate and one transaction. B splits one operation across two
stores with a partial-failure state (inactive but sessions still live), needs retry policy, and
adds a third copy of the `isActive` query. B's one advantage is that it would also clear Better
Auth `secondaryStorage`/cookie cache if we enable them later. In shape A, AuthGuard's per-request
staff lookup covers that case anyway, because it does not depend on the session row being gone
(see risks).

**Red-flag screen (shape A):**

- *Information leakage / two ways to do one task:* the "deactivated staff" rule would otherwise live
  in `assertSessionAllowed`, StaffGuard and AuthGuard. Fix: AuthGuard and the hook share
  `isDeactivatedStaff`. StaffGuard keeps its own query because it needs `role` and has a different
  rule (a missing row is denied). Leave a one-line comment there pointing to the difference so the
  next edit does not "unify" them wrongly.
- *Split ownership:* none. `removeStaff` stays the only writer of `staff.isActive`.
- *Shallow module / pass-through:* `isDeactivatedStaff` is a small function, but it is the policy,
  and two callers use it. Acceptable.
- Temporal decomposition, importable internals, hand-synced lists: none.

## 6. Architecture

```
DELETE /api/users/staff/:userId  (StaffGuard: caller is active staff)
  └─ removeStaff (single transaction)
       lock super-admins → lock caller → lock target
       ├─ target missing         → 404 (rollback)
       ├─ last super-admin       → 400 (rollback)
       ├─ target active          → UPDATE is_active=false ; DELETE session WHERE user_id
       └─ target already inactive→                          DELETE session WHERE user_id
     commit ──► 200 { success, alreadyInactive }
     any error ─► rollback ─► 500, staff still active, sessions untouched

Any AuthGuard route
  getSession(cookie) ── none ──► 401
       │
  userType === 'staff' ?
       ├─ no  ──► allow (scholars: no extra query)
       └─ yes ─► isDeactivatedStaff(userId)
                   ├─ no row (signup race) ──► allow
                   ├─ isActive=true         ──► allow
                   ├─ isActive=false        ──► 403 ACCOUNT_DEACTIVATED
                   └─ DB error              ──► 401 (fail closed)
```

**Security / race:** a target signing in *while* `removeStaff` runs. `assertSessionAllowed` reads
`staff.isActive` without a lock, sees the old committed `true`, and inserts a session row after our
`DELETE` but before our commit. That row survives the commit. This race exists today. The AuthGuard
leg closes it, because the next request sees `isActive=false` and gets 403, and StaffGuard already
blocks staff routes. Calling remove again (correction 2) deletes the row. It is not worth locking
the session table for this.

**Realistic production failure:** an RDS failover or connection drop during the transaction. With
shape A the transaction rolls back, the admin sees a 500 toast, and the staff member is still active
with their sessions intact. The state is consistent and retrying is safe. Under today's code the
same failure after commit gives 200 while the sessions stay live.

**Transaction cost:** the `DELETE` adds one indexed delete on `session.user_id` while the staff row
locks are held. A user has only a few session rows, so the extra lock time is negligible. Lock
order is unchanged, so this adds no new deadlock path.

**Distribution:** no new artifacts or migrations. The change ships with the normal API image.

## 7. Code quality notes

- `removeStaff` must not keep a `try/catch` that swallows errors. Remove the post-commit block
  entirely, and let the transaction's error propagate (Nest turns it into a 500).
- `AuthGuard`: keep `request.user` the same shape (`id`, `email`, `userType`). Do **not** add
  `staffRole` here. That stays StaffGuard's job.
- `AuthGuard` catch block: rethrow `UnauthorizedException | ForbiddenException`, as StaffGuard does.
  Today's bare `catch {}` would rewrite our 403 into a 401.
- `userType` gate: the ticket limits the check to `userType === 'staff'`, and this plan follows
  that so scholar requests do not pay for a query. `assertSessionAllowed` does not gate on
  `userType`. That difference is intentional: sign-in is rare, requests are frequent. Note it in the
  `isDeactivatedStaff` JSDoc.
- Update the `assertSessionAllowed` JSDoc. It currently says "StaffGuard still enforces access on
  every API request". After this change, AuthGuard does too.

## 9. Performance

- AuthGuard adds **one** `SELECT is_active FROM staff WHERE user_id = $1 LIMIT 1` per request, and
  only for `userType === 'staff'`. It is a unique-index probe. Request volume is unknown; the staff
  portal fires a few requests per page.
- No N+1 queries, no unbounded queries, no caching added. A per-request cache would defeat the
  point of the change.
- On staff routes that use both guards (none do today), the lookup would run twice. Accepted.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Staff app has no handling for 403 on `/api/users/me`, so a deactivated user sees error states rather than being signed out | Accepted for now. Removal also deletes the sessions, so the normal case is a 401 and the user is treated as logged out. The 403 only appears for leftover sessions. Frontend auto-sign-out on `ACCOUNT_DEACTIVATED` is the follow-up. |
| A staff user whose `userType` is wrong (`scholar`) with an inactive staff row would pass AuthGuard | Their sign-in is already blocked by `assertSessionAllowed`, which ignores `userType`, and StaffGuard requires `userType === 'staff'`. Low impact. Revisit if `userType` ever becomes editable. |
| Enabling Better Auth `cookieCache`/`secondaryStorage` later means deleting rows no longer revokes at once | AuthGuard's `isActive` lookup does not depend on the session row, so access stays blocked. Note this in the PR. |
| Changing `alreadyInactive` behavior surprises a caller | The only caller is the staff UI remove action. The response shape is unchanged. |
| A future edit wraps `removeStaff` errors and returns success again | The unit test "tx.delete rejects → removeStaff rejects" guards against it. |

## 12. NOT in scope

- Frontend auto-sign-out on 403 / `ACCOUNT_DEACTIVATED` (staff app `fetchAPI`, `useSession`).
- Moving AuthGuard-only staff routes (`/api/requests`, `/api/documents/:id/download`, `/api/files`,
  `/api/avatars/upload-url`, `/api/annual-updates/copy`, `/api/users/staff`) to StaffGuard.
- Scholar deactivation model.
- Microsoft OAuth login UX.
- Switching session revocation to Better Auth `internalAdapter` (shape B).
- Locking against the sign-in-during-removal race (covered by the AuthGuard leg instead).
